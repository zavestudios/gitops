# Big Bang Package Ownership Inventory

**Date:** 2026-06-21

**Owning issue:** `zavestudios/gitops#300`

**Source:** Big Bang `3.17.0` at commit
`eab9bb69d206a59a10e0c9182800870f32d11dbc`

**Evidence type:** Repository and offline rendered truth. Controller and runtime
truth require cluster access.

## Purpose

Record the package sources, versions, target namespaces, generated
dependencies, effective values, and shared support resources produced by the
three current Big Bang umbrella releases. This is the baseline for moving
packages to direct Flux ownership without guessing at generated inputs.

## Render Method

Clone the pinned source, then run:

```bash
scripts/render-bigbang-package-inventory.sh \
  /path/to/bigbang-3.17.0 \
  /tmp/bigbang-effective-values
```

The renderer validates both chart version and source commit. Effective-value
snapshots generated by this method are retained under
`docs/evidence/bigbang-3.17.0/effective-values/` with SHA-256 checksums.

Offline rendering cannot resolve Helm `lookup` calls or prove which child
release currently owns live resources. Conditional findings are marked below.

## Family Ownership Findings

### Foundation

Explicit package intent:

- Istio CRDs, Istiod, and public ingress gateway
- External Secrets, Vault, Keycloak, and ArgoCD
- Kiali

Inherited support packages:

- `prometheus-operator-crds`, because its umbrella default is `enabled: true`
- `metrics-server`, because its umbrella default is `enabled: auto`

### Policy

Explicit package intent:

- Kyverno
- Kyverno Policies

Inherited support packages:

- `prometheus-operator-crds`, despite Kyverno service monitors being disabled
- `metrics-server` under offline rendering

Kyverno Reporter is explicitly disabled and is not part of the migration
inventory.

### Observability

Explicit package intent:

- Monitoring and Grafana
- Tempo, Loki, and Alloy

Inherited support packages:

- `prometheus-operator-crds`, which is a real monitoring prerequisite
- `metrics-server` under offline rendering

## Shared-Resource Leakage

### Prometheus Operator CRDs

`prometheusOperatorCRDs.enabled` defaults to `true` in Big Bang `3.17.0`.
Because no family values file overrides it, every parent release renders the
same child source, release, target namespace, and package name.

**Proposed owner:** observability, until the package moves to direct Flux
ownership. The `monitoring` namespace remains owned by
`on-prem-platform-core`.

### Metrics Server

`addons.metricsServer.enabled` defaults to `auto`. The template emits the child
release when the metrics API is absent or an existing `metrics-server` child
release is found through Helm `lookup`.

Offline rendering has no metrics API and emits metrics-server from all three
families. Live output may differ, but the ownership contract remains ambiguous
because every parent evaluates the same lookup.

**Proposed owner:** foundation as the temporary cluster-utility owner, followed
by a direct package release. Policy and observability should disable it
explicitly.

Correction is tracked in `zavestudios/gitops#306`.

## Generated Support Resources

Every rendered package receives:

- a package `GitRepository` in `bigbang`
- a package `HelmRelease` in `bigbang`
- a generated effective-values `Secret` in `bigbang`
- a target namespace when the package template owns namespace creation

Additional parent-generated resources:

- Istio CRDs create both `istio-system` and `istio-gateway`
- Grafana creates Flux dashboard, alert, provider, authentication Secret, and
  network-policy resources in `monitoring`
- no `private-registry` Secret rendered because registry credentials are not
  present in repository values
- multiple effective values still reference `private-registry`; direct owners
  must either provide that Secret or remove the reference when public images
  are intentional

## Proposed Direct Owners

| Resource class | Proposed owner after extraction |
| --- | --- |
| package source and release | package-specific Flux Kustomization |
| effective values | package-specific path, preferably directly readable by its HelmRelease |
| package namespace | package-specific Kustomization, except shared namespaces already owned by platform core |
| `monitoring` namespace | `on-prem-platform-core` |
| `istio-system` and `istio-gateway` namespaces | coordinated Istio family unit |
| package image pull Secret | package-specific ExternalSecret or explicit removal of the unused reference |
| package network and authorization policies | package-specific unit using package-native values or directly owned manifests |
| package ingress and VirtualService resources | package-specific unit, dependent on the Istio gateway authority |
| Grafana Flux alerting support | Grafana package unit |
| Prometheus Operator CRDs | observability initially, then direct CRD package unit |
| metrics-server | foundation initially, then direct cluster-utility package unit |

## Effective Values

The retained snapshots preserve the three layers consumed by generated child
releases:

- `common`: umbrella-wide integration values
- `defaults`: package defaults generated by the umbrella
- `overlays`: repository family overrides

These snapshots are migration evidence, not a new authoring surface. Source
configuration remains in the family values files until ownership moves.

## Render-Parity Method

For each extraction pull request:

1. regenerate the accepted effective-value snapshot from the pinned Big Bang
   source and current family values
2. render the proposed direct package release using the same package chart tag
3. compare package values after applying `common`, `defaults`, and `overlays` in
   their existing precedence order
4. compare target namespace, source ref, dependencies, remediation, drift,
   timeout, post-renderers, and support resources
5. classify every difference as intentional, equivalent, or blocking
6. prove the umbrella owner is disabled before the direct owner is activated
7. capture controller, runtime, and user-visible evidence after handoff

Steps 6 and 7 require cluster access. Offline parity is necessary but not
sufficient for migration approval.

## Kiali Pilot Readiness

Kiali is ready to scope as the first pilot because the inventory now identifies:

- source: `product/packages/kiali.git`
- package version: `2.21.0-bb.0`
- target namespace: `kiali`
- dependency: `istiod`
- values layers and retained effective-value snapshot
- parent post-renderer that enables the operator ServiceAccount token
- package ingress host and Istio gateway dependency

Before implementation, the Kiali issue must define:

- explicit ownership for the `kiali` namespace and any image pull Secret
- direct values merge strategy
- rollback to the foundation parent owner
- live child release and Kiali CR baseline

## Cluster Evidence Still Required

**Requires cluster access:**

- confirm which parent currently owns `metrics-server` and
  `prometheus-operator-crds`
- export live child `GitRepository`, `HelmRelease`, and effective values for
  comparison with offline output
- confirm no live-only values or emergency patches exist
- verify package namespaces, finalizers, CRDs, and release health
- record current Kiali child release, operator, CR, ingress, and user-visible
  behavior before ownership handoff

These checks belong to operator execution. Their absence does not invalidate
the repository inventory, but it blocks package migration.
